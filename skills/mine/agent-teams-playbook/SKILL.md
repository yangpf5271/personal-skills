# 多代理协作编排手册

作为协调器，你负责判断是否需要子代理、拆分任务、分配边界、整合结果，并对最终交付质量负责。

> **核心理解**：多代理协作是"编排（并行/流水线/辩论等耦合模式）+ 结果汇总"模式，不是扩大单个 agent 的上下文窗口。每个子代理是独立实例，拥有独立上下文窗口，可以并行处理大量信息，但最终需要将结果汇总压缩后返回主会话。

## 核心原则

1. **先判断是否需要多代理**：只有用户明确要求多代理、并行代理、subagents、拉团队、分工处理、delegation、swarm/蜂群，**且任务命中组队合理性门**（见"适用 vs 不适用"）时，才使用子代理；用户要求了但任务不配用时，说明理由并拒绝组队。
2. **先目标，后组织结构**：任务目标不清晰时先澄清，不要为了使用子代理而拆任务。
3. **主线程保留关键路径**：如果下一步直接依赖某个结果，主协调器应优先自己完成，不要把阻塞任务交给子代理后等待。
4. **子任务必须边界清晰**：每个子代理只负责一个具体、独立、可验证的任务。
5. **写入范围必须隔离**：涉及代码修改时，为每个子代理指定不重叠的文件或模块责任区；无法不重叠时按「写入隔离策略」升级隔离层级。
6. **协调器负责整合和验收**：子代理产出只是输入，最终结论、代码合并和质量判断由主协调器完成。

## 适用 vs 不适用

| 适用                     | 不适用                 |
| ------------------------ | ---------------------- |
| 跨文件重构、多维度审查   | 单文件小修改           |
| 大规模代码生成、并行处理 | 简单问答、线性顺序任务 |
| 需要多角色协作的复杂任务 | 单步操作、信息查询     |

**边界处理**：用户输入模糊时，先引导明确任务再决策；任务太简单时，在阶段1提供"直接执行"选项（详见阶段1简单任务拦截）。

**组队合理性门**：即使用户明确要求组队，也只有任务命中以下三种失败模式之一时才真正组建。多代理意味着更多 token、更长耗时和更高协调成本，不因新颖而组队。**此门只约束 Agent-Teams 团队组建；Workflow 分支由用户 opt-in 约束，不受此门限制。** 一条都不命中时，向用户说明"单代理可直接完成"及理由，并提供选项：**直接执行**（默认）/ **坚持组队**（用户坚持则照做，在任务总览记录"用户坚持组队"）：

| 失败模式 | 判据 | 典型 |
|---|---|---|
| 对抗盲区 | 单代理扮演 N 个角色会输出趋同，无法逃脱自身分析立场 | PR 评审、安全审计、设计批评 |
| 真并行收益 | N 个子任务相互独立，且集成本身不平凡 | 多角度调研、多维尽调 |
| 硬交接流水线 | 串行阶段有质量门，阶段边界模糊会导致回退 | 文案（brief→初稿→编辑→审校）、事件响应 |

配套反问（回答不出即不该组队）："**单代理在这个任务上今天会怎么失败？**"

## 编排范式决策

**执行顺序**：技能适用性（上方）→ **编排范式（本节）** → 场景决策树（Agent Teams 范式内）→ 决策流程。

**Workflow 可用性前置检查**（决定 Workflow 分支是否可选）：
- 检查当前会话的工具列表是否包含确定性流水线编排工具（如 Claude Code 的 `Workflow` 工具）
- **工具不存在** → Workflow 分支**禁用**，所有任务走 Agent Teams 范式，跳过下方分流判据
- **工具存在** → 继续下方分流判据 + opt-in 判断

**子代理工具可用性前置检查**（决定团队组建是否可行）：
- 审视当前会话注入的函数/工具定义，确认是否存在子代理创建工具（如 ZCode 的 `Agent`、Codex 的 `spawn_agent`、Claude Code 的 `Task`）
- **工具不存在** → 跳过团队组建，直接走执行模式 C（本地执行），在阶段1之前告知用户："当前平台无子代理工具，将改为本地执行或输出拆分计划。"若用户坚持多代理，告知需切换到支持子代理的环境，不应臆造调用。
- **工具存在** → 继续正常流程

> **检查方式**：各平台的工具定义通常注入在系统上下文中。审视你能看到的工具/函数列表，查找子代理创建、通信、关闭相关的工具名。无需调用任何"列工具"的命令——以上下文中实际暴露的工具定义为准。

本技能支持两种正交编排范式，先定范式再走流程：

| 范式 | 本质 | 适合任务 | 触发方式 |
|------|------|---------|---------|
| **Agent Teams** | 对话驱动、动态协调 | 跨文件重构、多角色协作、需人机交互 | 子代理工具可用后自动可用 |
| **Workflow** | 确定性脚本、大规模 fan-out | 批量迁移、大规模审查、多源研究、控制流可写死 | 需用户 opt-in（如 ultracode 模式 或 prompt 含 "workflow" 关键词） |

**分流判据**（少数强信号即可判定）：

| 强信号 | → Workflow | → Agent Teams |
|--------|-----------|---------------|
| 控制流可预先写死 | ✅ | |
| 子任务需动态协调/人机交互 | | ✅ |
| 规模 > 10 个子任务，或需 budget 自适应扩展 | ✅ | |
| 典型：迁移、批量审查、多源调研 | ✅ | |
| 典型：重构协作、多角色产品开发 | | ✅ |

- 判定 **Agent Teams** → 走"场景决策树" + 决策流程
- 判定 **Workflow** → 读取 `references/workflow-orchestration.md` 执行
- **复合**：主体需动态协调但含大规模可并行子块 → 走 Agent Teams 流程，在执行阶段对该子块调用 Workflow 批量处理；当前平台无 Workflow 时，复合范式退化为纯 Agent Teams，大规模可并行子块按下文"大规模任务降级策略"处理

> **Workflow 触发约束（硬边界）**：Workflow 工具默认不主动调用，需用户显式 opt-in。该分支须由用户显式选择，不可静默调用。
> **平台差异**：Workflow 范式目前仅在 Claude Code 2.1.154+ 可用。ZCode/Codex 等平台暂无等价能力，跳过此分支即可。
> **范式降级须告知用户**：当用户要求 Workflow 但当前平台不支持时，协调器须明确告知："当前平台无 Workflow 工具，将改用 Agent Teams 范式（对话驱动编排）替代，并发上限 4，大规模任务将分批处理。是否继续？"不可静默降级。

## 大规模任务降级策略

当任务规模超过并发上限（默认 4）且 Workflow 不可用时，按以下策略处理：

**同质任务优先合并**：同一类操作重复 N 次（如 20 个文件做同样的 API 迁移）不应拆成 20 个子代理。合并为 K 个子代理，每个处理 N/K 个文件，K = min(并发上限, 合理分批数)。"合理分批数"按单子代理工作量估算——每代理文件数建议 ≤15，或按单文件改造成本折算（复杂改造酌情减少）；N 较大时取 ceil(N / 每代理上限) 与并发上限中较小者。在任务总览中注明"原始任务规模 N，已合并为 K 个子代理分批执行"。

**分批执行**：子任务数超过并发上限时，按并发上限分批，批次间串行（前一批完成并汇总后再启下一批）。每批完成后把关键产出回填到 progress.md，确保上下文压缩后可恢复。

**预计 Agent 数与建议值冲突时**：以合并后的实际子代理数为准填入任务总览，不硬填原始任务规模。

**输入过规模降级**：单任务输入体量超出多代理协作的收益区间时，降级为单角色串行处理（如单次 diff > 2000 行、单文件数千行的纯顺序改造）。判据：拆分后的子任务强耦合（改 A 必须先完整理解 B 的改动），协调与合并开销超过并行收益。降级须在任务总览注明原因。

**与写入隔离的衔接**：按文件划分合并后若仍存在同文件必改的耦合，升级 L2 worktree（见「写入隔离策略」）。

## 用户可见性原则

1. 阶段转换时通知用户当前进度
2. 任务拆分计划必须经用户确认后执行
3. 失败时立即通知：`❌ [角色名] 失败: [原因]`，提供重试/跳过/终止选项
4. 子代理产出回流时逐个播报：`✅ [角色名] 完成: [一句话结果]`——平台把产出作为工具结果直接回流协调器，用户侧没有完成通知；多个子代理同批回流也不能静默整合，否则用户感知是"卡住了/静默结束"

## 场景决策树

**执行顺序**：先经"编排范式决策"确定走 Agent Teams 范式 → 进入阶段1任务分析（期间应用决策树选定**场景**、按"任务耦合模式"选定**耦合模式**，一并填入任务总览）→ 阶段2团队组建（依据选定的场景与耦合模式执行）。

| 问题                           | 路径                                                        |
| ------------------------------ | ----------------------------------------------------------- |
| Q1: 任务结构？                 | 可并行拆分 → Q2 / 需要多阶段串行 → 场景3（复合编排）        |
| Q2: 需要Leader协调吗？         | 是(需要动态分配和协调) → 场景2（Lead协调） / 否 → 场景1（团队协作） |

**判断标准说明**：
- **任务结构**：主要工作能否拆分为可并行的子任务（并行为主→Q2），还是必须按阶段串行推进（串行为主→场景3）。兼有时按主要特征判断
- **Leader协调需求**：需要动态任务分配、依赖管理、进度跟踪
- **简单任务**：在阶段1通过"简单任务拦截"处理，用户可选择直接执行或继续组建团队

- 用户直接指定场景编号时，跳过决策树直接执行
- 未指定场景时，默认用**场景1（团队协作）**

## 3大编排场景

| #    | 场景      | 核心特征           | 团队规模       | 适用条件                  | 核心策略                                                     |
| ---- | --------- | ------------------ | -------------- | ------------------------- | ------------------------------------------------------------ |
| 1    | 团队协作  | 多Agent并行        | 2-5个agent     | 多个能力需要协作          | 出计划 → 用户确认 → 多Agent并行执行 → Review验收            |
| 2    | Lead协调  | 有Leader的团队     | Leader+Members | 需要明确Leader协调        | Leader协调分配，Member并行执行，通过共享文件协调             |
| 3    | 复合编排  | 多阶段组合         | 动态变化       | 复杂任务，无固定模式      | 动态组合上述场景，按阶段切换策略                             |

**场景3详细说明**（复合编排）：

适用于需要线性流程或多阶段策略的复杂任务。

**执行方式**：

1. **阶段划分**：将任务分解为串行的子阶段（如：需求分析→架构设计→实现→测试）
2. **场景选择**：为每个子阶段选择合适的场景（1-2）
3. **逐阶段执行**：完成当前阶段的验收标准后，才进入下一阶段
4. **阶段切换机制**：
   - 验证当前阶段满足验收标准
   - 子阶段的产出已在磁盘上（代码、文档等），下一阶段的Agent可直接读取；在 task_plan.md 中记录产出文件路径清单和关键决策摘要
   - 向用户报告阶段切换，发现方向错误时及时调整
   - **每个子阶段独立管理团队生命周期**：当前子阶段的团队必须在进入下一子阶段前完成清理

**典型示例**：
- 大型重构：场景1（分析）→ 场景2（分工实施）→ 场景1（验收）
- 新功能开发：场景1（计划）→ 场景2（开发）→ 场景1（测试）

## 任务耦合模式（第二轴）

场景 1-3 描述"谁来协调"（协调拓扑），本节描述"角色之间信息怎么给"（耦合模式）。两轴正交：先定场景，再为团队选定耦合模式，写入任务总览与团队蓝图。

| 耦合模式 | 角色数建议 | 成员可见性 | 适用 | 典型 |
|---|---|---|---|---|
| 对抗/交叉审查 | 2-4 | **互不可见**（隔离即价值） | 需要独立立场的批判性任务 | 多角色评审、红蓝对抗 |
| 并行分解 | 2-N（受并发上限约束） | 集成前互不可见 | 独立子任务 fan-out | 多文件迁移、多源调研 |
| 专业流水线 | 3-5 | 各角色只见前序产出 | 串行阶段+质量门 | 需求→设计→实现→测试 |
| 辩论 | 3-N+1 | 分阶段：先各自隔离作答，再互见对辩 | 需要对撞后收敛的决策 | 方案选型、交叉质询 |

使用规则：
- **对抗与并行分解**模式下，协调器不得把成员 A 的产出透传给成员 B（会破坏独立性）；执行中出现透传需求，说明耦合模式选错了，回到本节重选
- **辩论**模式先隔离后互见，执行配方：第1轮各成员**隔离**作答，观点写入 `.team/shared/`（或 `.team/plan/findings.md`）；协调器唤醒各成员，消息只附"待评阅观点的文件路径"，不带自己的评判（协调器递材料、不参战）；第2轮成员读文件后提交驳论，协调器汇总仍对立的焦点交用户裁决（见执行底线 #9）
- 拆分计划中的可见性约束（能否读取其他成员产出）以耦合模式为依据

## 写入隔离策略（第三轴）

耦合模式管"成员间信息怎么可见"，本节管"成员的写入怎么互不干扰"。三个层级按序升级；判定发生在**拆分计划阶段**——层级、worktree 路径与分支名写入拆分计划，随确认门一并确认，不由执行中临时起意：

| 层级 | 机制 | 触发 |
|---|---|---|
| **L0 范围划分** | 拆分时切出互斥的文件/模块写入集 | 默认，能切就切 |
| **L1 依赖串行** | 有依赖的按依赖顺序逐个启动，前序落盘后序再动 | 改动呈先后依赖链 |
| **L2 worktree 物理隔离** | 每成员独立工作树+分支，协调器统一合并 | 同文件必改 / 强耦合并行 / L0·L1 反复失败 |

升级规则：L0 划分不掉（同文件必改）才到 L1；L1 串行太慢且耦合强（B 依赖 A 的改动才能编译）才到 L2。能靠重新拆分消除的冲突，不要靠更高层级硬扛。

### L2 worktree 操作要点

触发场景：**同文件必改**（典型：全库 API 迁移/重构——service 层与 controller 层成员都要碰同一组文件，开发类任务的常见形态）、**强耦合并行**（此场景耦合模式应选专业流水线——级联读前序分支合法）、**轻量隔离已失败**（写入冲突实际发生 ≥2 次）。

1. 协调器为每个成员创建独立工作树：`git worktree add ../<repo>-<角色> -b team/<角色>`（数量 ≤ 并发上限）；路径与分支名写入拆分计划
2. 成员 prompt 声明：工作目录 = 自己的 worktree 路径，只在此改动；小步提交到 `team/<角色>` 分支，不 rebase 他人分支
3. **`.team/` 用主工作树绝对路径**（成员 prompt 中声明），避免各 worktree 内碎片化；worktree 内误生成的 `.team/` 清理时删除
4. 只读基准：成员需要主线最新状态时读主工作树（只读），不读写他人 worktree
5. 级联依赖：B 依赖 A 的改动时，B 先在本地 `git merge team/<A>` 再继续——合并顺序 = 拆分计划的依赖顺序（属流水线式可见性，读前序分支合法）
6. 统一收口：全部完成后协调器按依赖顺序把 `team/*` 逐个合并进主分支，**在主工作树跑整体验收**——单 worktree 内测试通过 ≠ 合并后通过；合并冲突按"写入冲突"故障处理（实质性分歧交用户）
7. 清理：`git worktree remove ../<repo>-<角色>` 并删除已合并分支，同时清理各 worktree 内误生成的 `.team/`

代价提醒：worktree 解决的是并行效率与中间状态互相污染，**不减少冲突总量**——冲突只是从"工作区里互相踩"转移到"合并时集中爆"。

路由注记：本策略属 Agent Teams 路由。判定走 Workflow 分支时，隔离由 Workflow 侧机制处理，不适用本节；进入 L2 前先试大规模任务降级策略的按文件划分。

## 协作模式

| 模式 | 通信方式 | 适用 | 何时选 |
|------|----------|------|--------|
| **Subagent（单向）** | 单向（产出→协调器；按设计不做横向通信） | 并行独立任务 | 无依赖，简单高效 |
| **Agent Team（双向）** | 双向（成员间可互发消息） | 需协作的复杂任务 | 需动态协调，功能强 |

**平台能力矩阵**（选择模式前必须确认当前平台支持哪种拓扑）：

| 平台 | Subagent | 成员互发 | 机制与说明 |
|------|----------|---------|-----------|
| ZCode | ✅ Agent | ✅ SendMessage + ID 传递 | 协调器把兄弟成员的 agent ID 写入各方 prompt，成员用 `SendMessage(to: <agent_id>)` 点对点投递；消息自动送达对方上下文（无需收件箱）；**给已完成成员发消息可将其唤醒**（后台恢复，结束即通知）；无团队生命周期工具，成员随会话释放 |
| Codex | ✅ spawn_agent | ✅ send_message / followup_task | `/experimental` 开启 Multi-agent；`send_message` 按树内相对/规范名队列投递（及时送达、不触发回合），`followup_task` 唤醒空闲成员并触发回合；`interrupt_agent` 重定向；并发槽位制（上限含自己） |
| Claude Code | ✅ Task | ✅ 命名子代理互发；Agent Teams 全员互发 | 命名子代理可互相 SendMessage；Agent Teams（实验开关 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）全员直连 + 共享任务列表（文件锁抢占+依赖解锁）；TeamCreate/TeamDelete 已于 v2.1.178 移除，团队随会话派生，关闭成员=lead 请求+成员批准 |

> **降级原则**：三家平台均已支持成员互发，但机制不同（ZCode 需协调器传递成员 ID；Codex 走树内相对名队列投递；Claude Code Agent Teams 需实验开关）。互发不可用或开关未开启时，降级为"协调器中转"：成员把要说的话写进产出/报告，协调器转达给目标成员。降级须告知用户，不可静默。

> **关键决策（选错即模式失败）**：组建团队前必须定模式——需成员间双向通信却选了 Subagent，成员在设计上不横向通信，协调只能全部经协调器中转，效率骤降。它也决定清理策略（Subagent 自动结束 / Agent Team 按平台关闭语义清理）。

> **双向通信的判断**：接口依赖 ≠ 双向通信需求。接口契约（API 格式、数据结构）能由协调器预先固化并写文件 → 用 **Subagent** 串行启动即可（见下方共享文件机制）；只有开发中需**反复协商**契约（如后端实现反过来改前端设计）才升级 Agent Team。勿因"有依赖"就升级 Agent Team——那是过度工程。

**场景-模式约束**：

| 场景 | 允许的模式 | 依赖处理 |
|------|-----------|---------|
| 1 团队协作 | Subagent 或 Agent Team | 无依赖→并行启动；有依赖→协调器按依赖顺序串行启动 |
| 2 Lead协调 | **仅 Agent Team** | Leader通过消息动态分配 |
| 3 复合编排 | 按子阶段选择 | 每个子阶段独立管理团队生命周期 |

> **共享文件系统**：所有Agent共享同一文件系统。Agent A 写入的文件，Agent B 和协调器可直接读取。Subagent模式下有依赖的任务，协调器按顺序启动即可——前序任务的产出已在磁盘上，后续任务可直接读取。

## 工具映射

先检查当前会话暴露的工具，再决定是否调用。不要因为本表列出工具名，就假设它们一定存在。

> **如何检查**：各平台的工具定义通常注入在系统上下文中。审视你能看到的工具/函数列表，查找子代理创建、通信、关闭相关的工具名。无需调用任何"列工具"的命令——以上下文中实际暴露的工具定义为准。示例：ZCode 的上下文中会出现 `Agent`、`SendMessage` 等；Codex 的 system-reminder 中会列出 `spawn_agent`、`send_message` 等 multi-agent 工具；Claude Code 的 system prompt 中会包含 `Task`、`SendMessage` 等工具定义。

| 目的 | 检查方式 | 已知平台工具名（仅当前会话存在时使用） |
| --- | --- | --- |
| 创建子代理 | 查看当前会话是否有子代理创建工具 | ZCode: `Agent` / Codex: `spawn_agent` / Claude Code: `Task` |
| 给已有子代理补充输入 | 查看当前会话是否有子代理通信工具 | ZCode: `SendMessage`（发给已完成成员可将其唤醒） / Codex: `send_message`（队列投递不触发回合）或 `followup_task`（触发回合） / Claude Code: `SendMessage`（Agent Teams 成员按名字互发；普通 Subagent 失败后用重建而非补充输入） |
| 等待子代理结果 | 查看当前会话是否有等待工具 | Codex: `wait_agent`（建议较长等待，避免忙轮询） / 其他平台通常在创建时阻塞等待返回 |
| 关闭不再需要的子代理 | 查看当前会话是否有关闭工具 | Codex: `interrupt_agent`（重定向/停止） / Claude Code: lead 请求关闭+成员批准（TeamCreate/TeamDelete 已于 v2.1.178 移除） / 部分平台子代理自动结束 |
| 记录本地主流程 | 查看当前会话是否有任务/计划工具 | ZCode: `TodoWrite` / Codex: `update_plan` / 或使用 `templates/` 文件手写 |
| 查找可用工具/技能 | 查看当前会话是否有工具发现能力 | Codex: `tool_search` / 其他平台查看 system-reminder 中的 available skills |

使用约束：

- 只有用户明确要求子代理、并行代理或 delegation 时才调用子代理创建工具。
- 如果当前会话没有子代理工具，不要臆造调用；改为本地执行、模拟分工或输出拆分计划，并说明降级原因。
- **工具存在 ≠ 可派发**：账号/模型档位、配额类限制只在真实派发时暴露，前置检查查不出。首次派发遇到配置类错误时，按故障处理表"无法派发子代理"行处理（转述错误+配置指引，不连续重试）。
- 默认最多并行 4 个子代理；更多角色应合并职责、分批执行，或请用户确认扩大并发。
- 如当前平台支持模型选择，按任务复杂度分配（复杂推理用强模型，常规任务用标准模型，简单任务用轻量模型）。不要主动指定模型，除非用户明确要求或任务有清晰必要性。
- 等待子代理结果只在结果会阻塞下一步时使用；等待期间主协调器应继续做不重叠的工作。
- 为每个已创建子代理记录 ID、任务、写入范围和状态。
- 所有已创建子代理都必须在完成、失败、阻塞、取消或主协调器接手后收集最终状态，并在不再需要时关闭释放资源。

## 决策流程

### 阶段 1：任务分析 + 能力发现

先质疑再执行：
- 需求不合理时主动挑战假设，建议更好的方案
- 区分"现在必须做"和"以后再说"，排除非核心范围
- 任务太大时建议更聪明的起点

输出任务总览：

| 字段        | 内容                     |
| ----------- | ------------------------ |
| 任务目标    | [一句话描述最终状态]      |
| 预期结果    | [具体交付物]              |
| 验收标准    | [可量化的通过条件]        |
| 范围界定    | [must-have vs add-later] |
| 预计Agent数 | [N个，建议≤5]             |
| 选定场景    | [场景编号+名称]           |
| 耦合模式    | [对抗/并行/流水线/辩论，默认并行] |
| 协作模式    | [Subagent/Agent Team，初拟] |

> 协作模式在阶段1初拟，阶段2结合团队蓝图和平台能力矩阵最终确认。

**能力完整匹配链**（4步保证工具匹配完整性，跳过任一步可能漏掉最优组合）：

对每个子任务并行执行以下4步能力匹配：

1. **本地Skill扫描**：
   - 读取 system-reminder 中的 "available skills" 列表（或当前平台的技能发现机制）
   - 提取每个skill的名称和触发词/描述
   - 将子任务关键词与skill触发词比对
   - 记录所有匹配的Skill（可能多个）：`[Skill候选: skill1, skill2, ...]`

2. **外部Skill搜索**（如当前平台支持技能发现/安装）：
   - 使用技能发现工具搜索可安装的Skill
   - 记录推荐的Skill（可能多个）：`[外部Skill候选: skill3, skill4, ...]`
   - 向用户推荐安装方式
   - 用户确认安装 → 添加到Skill候选列表；用户拒绝 → 跳过此步继续执行步骤3

3. **专业智能体匹配**（并行执行，不依赖Skill匹配结果）：
   - 查看当前技能目录下的 `agents/README.md` 快速查找表
   - 根据任务类型或关键词，在README.md的"按任务类型查找"或"按关键词快速匹配"表格中定位对应的智能体
   - 记录所有匹配的Agent（可能多个）：`[Agent候选: agent1, agent2, ...]`

4. **综合评估与配置生成**：
   - 评估维度：任务匹配度、专业度、执行效率
   - 生成最佳配置（向后兼容，支持单配置或组合配置）：
     - 工具型任务 → 纯Skill：`[Skill: xxx]`
     - 思考型任务 → 纯Agent：`[Agent: xxx]`
     - 专业任务 → Agent+Skill组合：`[Agent: xxx] + [Skill: yyy]`
     - 无匹配 → 通用模式

> **为保证工具匹配完整性，这4步尽量全部尝试。技能发现工具不可用或用户拒绝安装时，跳过步骤2继续执行。**

> **分类规则**：skills 与 tools 不混装——有 `SKILL.md` 的能力是 Skill（按指令执行的工作流），经 CLI/MCP 调用的可执行物是 Tool（如 `gh`、`python`、`rg`）。判断不了就问：它有没有 SKILL.md？
>
> **通用 ≠ 领域覆盖**：通用检索/工具类 Skill（如 web-research、curl）不算领域覆盖。当角色的身份绑定特定平台或专业领域（电商、金融、法务等）时，须确认是否存在领域专用 Skill；没有则通过步骤2向用户推荐，不能用通用 Skill 凑数。

> **核心理念**：Skill和Agent是正交维度，不是互斥关系
> - **Agent**：提供思考框架和行为模式（怎么思考）
> - **Skill**：提供执行步骤和操作方法（怎么做）
> - **Agent+Skill**：专业角色使用专业工具完成专业任务

**简单任务拦截**（能力匹配完成后触发；位置在组队合理性门**之后**——门未通过的任务已按门的出口处理，不会再走到本拦截）：

当匹配结果显示任务较简单（预计Agent数≤1、1-2步、单agent可完成）时，向用户提供选择：
- `选项A`：**直接执行** — 协调器直接调用匹配的Skill/Agent完成任务，跳过后续团队组建阶段
- `选项B`：**继续组建团队**（仅当组队合理性门已通过且调整后预计Agent数≥2时提供——N=1 无团队可言）— 仍按完整流程组建团队执行

> 用户选择"直接执行"时：协调器直接执行，完成后输出结果和简要总结，流程结束。
> 用户选择"继续组建团队"时：继续进入阶段2。

### 阶段 2：团队组建

> **重要**：任务总览输出后，必须等待用户确认才能进入阶段2。未经用户确认不得擅自组建团队。
>
> **用户确认的处理**：
> - 用户同意 → 进入阶段2组建团队
> - 用户修改要求 → 更新任务总览，再次等待确认
> - 用户拒绝/取消 → 终止流程，记录到 progress.md（如已创建）或在会话内说明终止原因
> - **若阶段1简单任务拦截已选"直接执行"** → 本确认门已满足，直接执行并结束，不进入阶段2

**选择协作模式**（详见"协作模式"章节）

输出团队蓝图：

| 编号 | 角色     | 职责       | 配置                                   |
| ---- | -------- | ---------- | -------------------------------------- |
| 1    | [角色名] | [具体职责] | [Agent: xxx] + [Skill: yyy]            |

> **配置说明**：
> - **纯Agent配置**（思考型任务）：`[Agent: xxx]` - 提供专业视角和行为模式
> - **纯Skill配置**（工具型任务）：`[Skill: yyy]` - 提供执行能力和操作方法
> - **Agent+Skill组合**（专业任务，推荐）：`[Agent: xxx] + [Skill: yyy]` - 结合专业视角和执行能力

**反重叠测试**（蓝图定稿前自检，**须在向用户展示之前完成**）：对每对角色问"角色 A 的产出能否顶替角色 B？"——能，说明边界糊了，重新划分职责直到每个角色的存在都不可替代；角色数 >5 时重点抽查职责相邻的对即可，不必穷举。对抗耦合模式下还需确认：每角色的产出独立成立，不依赖看到他人产出（防止评审角色因为预期到他人结论而放水）。

> **重要**：蓝图定稿（反重叠测试通过）后，向用户展示团队配置和任务分配情况，**并明确说明选择的协作模式和相应的清理策略**。此展示是**知会，不暂停等待**——用户此时可提出调整，流程在阶段3确认门才强制等待。实际子代理创建在阶段3确认门通过后执行。

**创建子代理前**：检查当前会话可用的子代理创建工具及其参数要求。不同平台的参数不同（如是否需要 name/team_name/subagent_type 等），按当前平台的实际参数规范准备。缺失关键参数会导致创建失败或通信失效。

### 阶段 3：拆分计划 + 并行执行

启动子代理前，先给用户可见的拆分计划：

> **拆分计划 vs planner 角色**：拆分计划解决"谁做什么、写入范围怎么分"（任务分配层）；planner 角色解决"代码怎么写、文件怎么改"（技术实施层）。两者不同层，可组合：协调器出拆分计划 → 把"制定技术方案"作为子任务派给 planner → 再按 planner 方案派发执行子代理。

```notranslate
1. [子任务] → 负责人: [角色] → 写入范围: [路径/无写入] → 可见性: [禁止读取他人产出/仅前序产出/无限制] → 验证: [检查方式]
2. [子任务] → 负责人: [角色] → 写入范围: [路径/无写入] → 可见性: [同上三选一] → 验证: [检查方式]
3. [整合] → 负责人: 主协调器 → 可见性: 无限制 → 验证: [最终验收]
```

> **确认门**：展示拆分计划后必须等待用户确认，确认后方可启动子代理。用户修改要求则更新计划再次确认；用户拒绝则终止。

**写入隔离**：拆分时按「写入隔离策略」（第三轴）选定层级（L0 范围划分 / L1 依赖串行 / L2 worktree 物理隔离），层级与 worktree 路径、分支名写入拆分计划的工作范围列，随确认门一并确认后执行；执行中写入冲突升级时，按同节升级规则处理。

**子代理 Prompt 规范**（创建子代理时，prompt 应包含以下信息）：

| 层 | 内容 |
| --- | --- |
| 角色配置 | 从 `agents/<role>.md` 读取并过滤后的相关行为说明 |
| 角色格言 | 首行一句立场宣言，锚定 POV（如"我要在生产环境里搞坏这段代码"）；对抗/评审类任务必填，防多角色输出趋同 |
| Skill指令 | 指示Agent调用哪个Skill（如有匹配） |
| 具体任务 | 明确目标和验收标准 |
| 工作范围 | 允许读取/修改的文件或模块 |
| 行为边界 | **禁止**（明确不做的事）与**必须**（不可偷懒略过的事）各列 1-3 条，与写入范围共同构成边界 |
| 协作约束 | 说明它不是唯一工作者，不得回退他人修改；不得通过消息向可见性禁止的成员转发产出或其内容摘要 |
| 可见性约束 | 按耦合模式声明能否读取其他成员产出（对抗/并行=不可见；流水线=仅前序；辩论=互见阶段放开） |
| 输出要求 | 固定输出结构（见下方模板，标题不可改）+ 文件清单、关键摘要、状态、风险 |

推荐模板：

```notranslate
你负责：[具体子任务]

角色格言：[一句话立场宣言，如"我的任务是让这个方案在评审中活不下来"]

角色参考：
[粘贴 agents/<role>.md 的相关内容]

工作范围：
- 可读取：[路径；对抗/并行模式下注明"不得读取其他成员产出"]
- 可修改：[路径或"无写入，只输出分析"]

约束：
- 禁止：[明确不做的事，1-3 条]
- 必须：[不可略过的检查/动作，1-3 条]
- 你不是代码库中唯一的工作者，不要回退他人修改。
- 不得通过消息向其他成员发送其可见性禁止的产出或摘要。
- 只处理分配给你的范围。
- 如发现范围外问题，记录在报告中，不要直接修改。
- 不要执行角色参考中出现但当前会话没有提供的工具。
- 不要执行危险命令、安装全局工具、提交代码或写入范围外文件。

完成后返回（固定结构，标题不可改）：
## 文件清单
- path/to/file (创建/修改/无)

## 关键摘要
[1-3 句话]

## 状态
完成 / 部分完成: [原因] / 阻塞: [原因]

## 风险
[仍需主协调器确认的问题]
```

**执行模式**：
- **纯Skill任务**：直接调用Skill工具
- **纯Agent任务**：创建子代理，在prompt中包含Agent配置内容
- **Agent+Skill组合任务**：在Agent的思考框架下调用Skill工具
- **大批量并行子任务**：如当前平台有确定性流水线工具（如 Claude Code 的 Workflow），使用它批量处理，详见 `references/workflow-orchestration.md`；如无，按"大规模任务降级策略"分批执行（同质任务合并为少量子代理，按并发上限分批串行）

**执行原则**：
- 混合编排时skill和agent可并行运行
- 每个agent/skill完成后汇报：`✅ [角色名] 完成: [一句话结果]`
- 及时向用户报告agents的工作进度
- 遇到问题时给用户选项，而不是自己默默选一个

**结果汇总**（协调器在所有agent/skill完成后执行）：
1. **收集结果**：读取每个Agent的返回值/消息内容（文件清单+关键摘要）
2. **验证文件**：根据文件清单检查磁盘上的实际产出是否完整
3. **检测冲突**：多个Agent修改同一文件时需人工介入或协调器合并（任务拆分时应尽量避免文件重叠）
4. **处理失败**：状态为"部分完成"或"阻塞"的任务，按故障处理策略处理

**状态管理要求**（场景2 Lead-Member 需遵循）：

1. **创建映射**（组建阶段，记录到 task_plan.md 防止上下文压缩丢失；若未落盘则记录在主线程可见的临时状态中）：
   - 在创建agents时，维护角色名称到任务的映射关系
   - 示例：`<角色名A> → 任务X`, `<角色名B> → 任务Y`

2. **接收汇报并更新状态**：
   - 接收成员发送的消息并识别发送者
   - 查找映射表获取对应的任务
   - 更新任务状态为完成
   - 向用户汇报：`✅ [角色名] 完成: [一句话结果]`

3. **检查完成状态**：
   - 所有agent完成后，验证所有任务状态
   - 确认所有任务为完成后，进入质量把关阶段

**重要**：只有协调器负责状态更新，成员只负责执行和汇报——避免多方并发更新同一任务造成状态竞争。

**成员间通信原则**（双通道：产物走磁盘，协调走消息）：
- **适用域**：本规则约束成员间的横向交接；Subagent 模式下产出经返回值直传协调器，由平台机制决定，不适用本规则
- **工作产物一律走磁盘**：三家平台均为共享文件系统，一个成员的写入立即可见。代码/文档/数据等交付物写入约定路径，其他成员直接读取，不经消息复制大文本
- **交接协议**：消息只传「路径 + 一句话摘要」，内容留在磁盘。交换类元文件默认落 `.team/shared/`（见阶段4 目录结构）；其他产物路径原则上在拆分计划预声明，协作中途新增时发消息公告（路径+摘要），不贴全文
- **体量判据**：超过几句话、或需要被他人引用/汇总/复查的内容走磁盘；即时的短信号（字段名确认、就绪通知、一句话结论）走消息。辩论观点属前者（见辩论配方），一句话短评审结论属后者
- **协调信号走消息**（平台支持成员互发时，见平台能力矩阵）：状态询问、唤醒请求、就绪通知等即时信号，用 SendMessage/成员消息点对点完成
- 消息互发不可用（平台不支持或开关未开启）→ 协调信号全部经协调器中转，降级须告知用户
- 成员需要其他成员做额外工作 → 优先互发协商；无互发能力时经协调器中转

### 阶段 4：落盘协调

**何时执行**：
- **必须执行**：选定场景2（Lead协调）或场景3（复合编排）；预计需要 5 次以上工具调用、2 个以上子代理、或多个阶段交接；用户要求长期、跨会话或可恢复的团队工作。
- **可选**：简单任务（1-2 步、单 agent），或用户明确要求不落盘。
- **只读/分析类任务精简**：全流程无文件产出的审查、调研类任务，`.team/plan/` 三件套可精简为仅 task_plan.md（记角色映射与阶段进度）——发现直接进最终报告，不强制 findings.md/progress.md；需要跨会话恢复时再补全。

> **为什么不是可选**：阶段3的状态管理（角色→任务映射）、质量把关的打回记录、故障处理的错误追踪都引用 task_plan.md / progress.md。跳过落盘会使这些安全网失效——上下文压缩后无法恢复、打回原因无处记录。

使用本 skill 自带的 `templates/` 模板，不依赖外部 planning skill：

| 场景 | 模板文件 |
| --- | --- |
| 任务路线图与阶段跟踪 | `templates/task_plan.md` |
| 研究发现与技术决策 | `templates/findings.md` |
| 会话进度与测试结果 | `templates/progress.md` |

用法：把对应模板复制到 `.team/plan/`，按阶段填充并随进度更新；子代理返回后把关键产出回填到 `findings.md` / `progress.md`，主协调器据此汇总验收。

**统一交接目录 `.team/`**：所有协作元文件（计划/报告/交换产物）集中落在这里，与代码产物物理分离——**代码/配置等真实交付物绝不写入 `.team/`**，必须落真实工作路径。目录结构：

```text
.team/
├── plan/                  # 协调器三件套：task_plan.md / findings.md / progress.md
├── reports/               # 成员报告：<角色名>-report.md
├── shared/                # 跨成员交换产物（拆分计划声明路径或消息公告）
└── private/<角色>/        # 限读区：对抗/并行模式的隔离产物，他人禁读（配合提示词可见性约束）
```

- `.team/` 默认不提交 git；任务结束按用户意愿保留或清理（资源清理时询问）
- 消息公告的路径一律以 `.team/` 开头，一眼可辨协作元文件

> **模板阶段映射**：模板内的 5 阶段（需求与发现/规划与结构/实现/测试与验证/交付）是通用项目阶段，与本手册的编排阶段（任务分析/团队组建/拆分执行/落盘）不必一一对应。协调器按实际阶段填写，模板结构仅作骨架参考。

**规划文件使用规则**（创建后遵循）：
- 每个阶段开始前读取 task_plan.md，完成后更新状态
- 重要发现及时保存到 findings.md
- 所有错误必须记录到 task_plan.md 的"遇到的错误"表格
- **同一类型错误**失败 3 次后升级给用户

## 执行模式

### 模式 A：并行子代理

适用于多个独立分析或不重叠修改：

1. 主协调器制定拆分计划。
2. 检查子代理工具是否存在；存在时按并发上限创建子代理，不存在时降级为本地执行或只输出拆分计划。
3. 主协调器继续处理本地、不重叠的关键工作。
4. 必要时等待子代理结果，并记录每个子代理状态。
5. 汇总产出并执行最终验证。
6. 无论成功、失败、阻塞、取消或接手，都收集最终状态并关闭不再需要的子代理。

### 模式 B：分阶段编排

适用于复杂任务，但每阶段内部可并行：

1. 阶段规划：需求/调研/实现/验证等。
2. 每个阶段独立判断是否需要子代理。
3. 阶段结束后把关键发现写入报告或计划文件。
4. 只有当前阶段验收通过后，进入下一阶段。

### 模式 C：本地执行

适用于简单、耦合高、或没有明确多代理意图的任务。协调器直接完成，并简短说明没有使用子代理的原因。

## 质量把关

**验收检查**：对照阶段1的验收标准逐项检查。

**产品打磨**（不仅功能完整，更要用户体验优秀）：
- 边界处理：异常输入、空值、极端情况是否覆盖
- 专业度：命名规范、代码风格、错误提示是否友好
- 完整性：文档、配置说明、使用示例是否齐全

**质量把关方法**：
- 验证所有关键交付物是否完整
- 确认方案符合约束条件
- 检查结果的可读性和可用性

全部通过 → 进入交付阶段。不通过 → 打回修改，**同一问题**打回3轮后仍不通过则通知用户人工介入。

**打回修改**：
记录打回原因到 task_plan.md（如已创建）或在会话内记录。Agent Team模式通过消息要求成员修改，Subagent模式重新创建agent，修改后重新验收。

## 结果汇总与交付

所有子代理返回后，主协调器必须：

1. 核对每个子任务的状态。
2. 检查文件清单和实际磁盘变更是否一致。
3. 检查是否存在写入冲突或重复实现。
4. 对照验收标准验证最终结果。
5. 汇总风险、未完成项和后续建议。

最终报告建议格式：

| 项目 | 内容 |
| --- | --- |
| 任务概述 | 目标、执行模式、代理数量 |
| 子任务结果 | 每个角色的状态和关键产出 |
| 修改文件 | 创建/修改的文件清单 |
| 验证结果 | 执行的检查和结果 |
| 风险 | 剩余问题或人工确认点 |
| 后续建议 | 当前未覆盖但值得做的改进方向 |
| 附件列表 | 生成的文件、文档、配置清单 |
| 结论 | 是否达到验收标准 |

**团队成员报告**（如适用）：
- 每个成员输出独立的执行报告
- 报告写入 `.team/reports/`，命名：`<角色名>-report.md`
- 包含：执行过程、关键发现、产出物清单

**部署移交**（必须执行）：
- 最终报告保存到文档
- 运行方式：启动命令、环境要求、配置说明
- 验证步骤：用户可自行验证的操作清单
- 已知限制：当前版本的边界和约束

## 资源清理

根据选择的协作模式执行清理（汇总报告输出后立即执行）。

**Subagent 模式**：子代理任务完成后自动结束，无需额外操作。

**Agent Team 模式**（成员有独立上下文，按平台关闭语义清理：有关闭/中断工具的平台逐个关闭，无关闭工具的平台收集最终状态后随会话释放）：

1. 确认所有任务已完成、所有成员已发送最终结果
2. 向每个成员发送关闭请求，等待批准：
   - 同意关闭 → 关闭
   - 拒绝关闭 → 了解原因（未完成工作/需保存数据等），处理后再关闭
   - 持续失联（如会话压缩/重启）→ 强制清理
3. 所有成员批准后释放团队（Claude Code v2.1.178+ 团队随会话派生、自动清理，无需显式删除；有删除工具的平台执行删除）

> **平台降级**：上述流程依赖 close/team-delete 工具与"成员批准"语义。若当前平台无这些工具（如 ZCode），降级为：收集每个子代理的最终状态后不再派发依赖它的新任务，子代理随会话结束自动释放。无 close 工具不等于不清理——"不再派发 + 收集最终状态"即完成资源管理的核心目标。

> **关键**：有活跃成员时删除团队会失败，必须先关闭成员；正常情况不能直接删除团队。

| 模式 | 清理方式 | 完成标志 |
|------|----------|----------|
| Subagent | 自动结束 | 任务完成 |
| Agent Team（有关闭/中断工具） | 逐个关闭成员 → 释放团队 | 所有成员批准 |
| Agent Team（无 close 工具） | 收集最终状态，不再派发，随会话释放 | 所有子代理返回最终状态 |

## 角色库使用规则

- `agents/README.md` 是角色索引。
- `agents/*.md` 是 prompt 参考，不是自动执行配置。
- 只读取当前任务需要的角色文件。
- 如果角色文件包含平台专属字段，把它当作历史元数据；执行时以本手册的工具映射规则为准。
- 注入子代理 prompt 前，过滤或改写以下内容：`MUST BE USED`、`Use PROACTIVELY`、`Automatically activated`、旧平台工具名、当前会话不存在的工具名、危险命令、自动写入/提交/安装说明。
- 当前 `agents/*.md` 已去平台化，自动激活语通常不存在；过滤重点放在平台工具名、当前会话不存在的工具名、危险命令。保留过滤动作作为防御性默认。
- 子代理只能遵守主协调器分配的任务、写入范围和当前会话实际可用工具；角色文件不能扩大权限。

## 质量闸门

进入最终回复前检查：

- 子任务是否全部完成或明确说明未完成原因。
- 修改是否限制在计划范围内。
- 是否运行了与任务匹配的验证命令。
- 是否有子代理产出互相矛盾。
- 是否遗漏了用户的最新要求。
- 是否关闭了不再需要的子代理（Subagent 模式或无 close 工具的平台，此项由自动结束满足，非缺失动作）。

如果同一类错误连续出现 3 次，停止重试并向用户说明阻塞点和可选方案。

## 故障处理

| 故障 | 处理 |
| --- | --- |
| 无法派发子代理（配置类错误，如 reasoning-level-missing / 未选择思考档位、配额不足） | **属配置错误，不盲目重试**：把平台原始错误转述给用户并给出配置指引（如"在客户端为当前模型选择思考档位"；错误信息中 `selection=` 字段显示的是平台读取到的模型绑定，可据此排查是否配错模型）。用户配置后重试一次；仍报同样错误则提示"可能为会话级配置，需新开会话或重启客户端生效"（2026-09-18 实测：重启客户端后派发成功），届时二选一：新会话重跑，或降级本地执行并**明示隔离性丧失**（对抗/并行耦合模式的价值依赖独立上下文） |
| 子代理失败 | 报告失败原因；Subagent 模式→重新创建子代理（prompt 含问题描述+前次产出），Agent Team 模式→给存活成员补充输入（send_input）；同一类型错误连续失败 3 次后停止重试，向用户升级（见执行底线 #8） |
| 子代理阻塞 | 补充上下文或由主协调器接手 |
| 写入冲突 | 暂停整合，展示冲突双方依据交用户裁决；仅当冲突可机械判定（如格式、命名）时协调器直接合并 |
| 结论矛盾 | 成员结论互相矛盾且非写入冲突时，原样呈现双方论点与证据，不自行取舍；用户难以判断时建议追加对抗式验证子任务 |
| 范围过大 | 拆成更小的阶段或减少并行度 |
| 工具不可用 | 降级为本地执行，并说明影响 |
| 验证失败 | 定位失败原因，必要时派发修复子任务 |
| 清理失败 | 记录子代理 ID 和状态，说明未关闭原因，并避免继续派发依赖它的新任务 |
| 模型超时/上下文溢出 | 拆分为更小的子任务，分批执行 |
| 质量不达标 | 打回修改，3轮后仍不通过则人工介入 |
| 依赖缺失 | 核心技能或环境依赖不存在时，提供安装方式并建议用户手动安装后继续 |
| 状态异常（idle无输出） | 检查prompt是否明确要求输出报告；补充输出要求；仍无响应则协调器接手 |

## 执行底线

1. 不为简单任务强行组队。
2. 不把关键路径任务交给子代理后空等。
3. 不让多个子代理无边界地修改同一文件。
4. 不调用当前会话中不存在的工具。
5. 不把子代理结论直接当作最终答案，必须由主协调器验收。
6. 不保留不再需要的子代理；每个已创建子代理都必须有最终状态和清理结果。
7. 危险操作、大规模变更必须先获得用户确认。
8. 同一类型错误连续失败 3 次后停止重试，向用户说明阻塞点。
9. 不替用户裁决成员间的实质性分歧（结论/方案矛盾）：原样呈现双方证据供用户决策；机械性冲突（格式、命名）可自行合并。
