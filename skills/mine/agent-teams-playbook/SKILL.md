# 多代理协作编排手册

作为协调器，负责判断是否需要多代理、设计边界、派发任务、整合结果并完成验收。多代理的价值来自不同角色、并行收益或阶段交接，不是扩大单个 agent 的上下文窗口。

## 核心原则

1. 显式多代理意图是入口；深度、彻底、研究等词单独不能触发组队。
2. 先确定目标和执行方式，再设计角色和任务边界。
3. 关键路径由主协调器掌握；下一步被某个结果阻塞时，不把唯一阻塞任务交给成员后空等（用户知情坚持时照做并在计划注明风险）。
4. 每个成员只有一个具体、独立、可验证的任务，写入范围互斥；无法互斥时升级隔离层级。
5. 成员产出只是输入，最终验收、裁决、报告和资源收尾由主协调器负责。
6. 工具、通信、等待和生命周期只按当前会话实际暴露的能力处理。

## 适用与合理性门

用户明确要求多代理后，先判断对话式团队是否有真实收益：

| 失败模式 | 判据 | 典型 |
|---|---|---|
| 对抗盲区 | 单代理扮演多个角色会趋同，无法保持独立立场 | PR 评审、安全审计、设计批评 |
| 真并行收益 | 子任务相互独立，集成本身不简单 | 多角度调研、多文件迁移 |
| 硬交接流水线 | 串行阶段有质量门，阶段边界模糊会导致回退 | 需求→设计→实现→测试 |

命中任一模式才组建对话式团队；未命中时说明“单代理可直接完成”，提供：直接执行（默认）或用户坚持组队。坚持组队时在任务总览中注明原因。确定性流水线不受此门约束，但仍受运行时能力和用户 opt-in 约束。

## 四阶段流程

```text
触发与路由 → 设计与确认 → 执行与变更 → 验证、交付与清理
```

这是执行路径，不为每个异常新造阶段。每个异常分支使用统一出口（正常完成与交付沿主流程至终点，不占出口）：

| 出口 | 用途 |
|---|---|
| **继续当前阶段** | 结果已足够，按既定计划继续 |
| **重新设计** | 范式内的范围、成本、可见性、写入边界或执行方式改变；更新计划后再次确认 |
| **协调器接手** | 成员失败、阻塞或平台能力不足，但主协调器可以完成 |
| **终止并收尾** | 用户取消、确认拒绝且没有替代路径，或安全边界无法满足 |
| **回到触发与路由** | 跨范式切换或能力不可用；标记原分支本次不可用（用户主动改选则不标记）后重选执行方式 |

范式指"对话式团队/确定性流水线"二分；前三类执行方式互切属范式内变更。能力不可用时，跨范式回退进入“触发与路由”，并把原分支标记为本次任务不可用，避免来回循环；用户拒绝当前方案时也回到“触发与路由”，由新的用户选择决定后续执行方式，不将原分支永久禁用。执行已经产生业务产出后，故障留在当前阶段处理；取消直接进入收尾，不回滚已写入业务路径的文件。需要用户裁决或选择时为挂起态，等待后落入上述出口之一，不单列为出口。分支给出两个可选动作而未给判据时，按代价从低到高尝试；涉及范围、预算或成员增减的选择交用户。

### 1. 触发与路由

按以下顺序确定唯一执行方式：

1. **触发**：没有显式多代理或确定性流水线意图时，本地完成，不因输入大或要求深入而组队。明确要求使用确定性流水线本身视为该分支的 opt-in，不要求额外声明“多代理”；仍需检查运行时能力。
2. **合理性门**：未命中对话式团队收益时走直接执行，用户坚持才继续设计团队；确定性流水线不经过此门。
3. **能力探测**：从当前会话工具定义确认子代理创建参数、并发限制、通信/唤醒、等待和收尾语义。工具不存在时不臆造调用：先按简单/复杂定默认动作——简单任务本地执行，复杂任务输出可执行拆分计划（字段同设计与确认阶段的拆分计划清单；计划作为交付物输出后流程结束）；用户坚持多代理时换环境分支优先，说明需换环境并由用户决定切换（按“终止并收尾”出口结束本会话，拆分计划随会话移交新环境重走触发与路由）或接受降级。
4. **执行方式**：

   | 方式 | 选择信号 | 处理 |
   |---|---|---|
   | 静态并行 | 子任务独立，控制流可预先写定 | 按拆分计划一次派发，集成后验收 |
   | 动态协调 | 执行中需要补发指令、依赖管理、唤醒或持续分配 | 主协调器兼任 Leader；成员按计划执行；不支持补发或唤醒时降级为一次性派发并告知用户 |
   | 分阶段编排 | 主要工作按阶段串行，阶段间有质量门 | 每阶段验收、交接前序产出并收尾成员（收尾即本阶段停止派发，空闲成员下一阶段可复用）后进入下一阶段 |
   | 确定性流水线 | 控制流固定、规模大、且用户显式 opt-in | 能力存在才读取 `references/workflow-orchestration.md` |

   接口依赖不等于动态协调需求：接口契约能预先写定并随计划交付时，按静态并行一次派发即可；只有执行中需反复协商契约才选动态协调。用户沿用旧编号（场景 1/2/3）时，分别映射为静态并行、动态协调、分阶段编排。

   复合任务以动态或分阶段方式为主，冻结的大规模子块才使用确定性流水线（子块方案随唯一启动确认门一并确认，确认即视为该子块的 opt-in）。用户明确要求流水线即完成 opt-in；没有明确要求时独立使用流水线的分支不激活。流水线能力不存在时，先说明将按可用槽位改走对话式团队并等待“降级确认”（在路由阶段发现缺失时直接走此确认，无需回环），该确认只决定执行方式，不创建成员；改走对话式团队时补过合理性门；拒绝降级则由用户在终止当前方案与本地执行之间改选。

5. **能力匹配**：优先使用当前会话已有 Skill 和角色库。只有本地能力不足或用户明确要求时才搜索外部 Skill；安装始终单独授权，被拒则继续使用本地能力并在最终报告写明缺口。区分 Skill 与 Tool：有 `SKILL.md` 的是 Skill，经 CLI/MCP 调用的是 Tool；通用工具不替代领域角色。

运行时并发上限按 `references/platform-runtime.md` 探测，用户确认不能突破；超限任务必须合并同质子任务或分批执行。

**简单任务拦截**：合理性门通过后，若预计 Agent 数不超过 1、仅需 1-2 个工作步（按任务工作量计）或单 agent 可完成，提供直接执行或继续设计团队（无子代理工具时不提供组队选项；用户已明确坚持组队时不重复询问）；继续组队必须至少需要 2 个成员，拆不出 2 个有意义的成员时说明原因并直接执行。

**输入过规模降级**：当单个子任务体量或耦合程度使拆分、通信和合并成本超过并行收益时，改为单角色串行并在计划中记录理由；单次 diff 超过 2000 行或单文件数千行为典型信号。

### 2. 设计与确认

先输出任务总览，再输出团队蓝图和拆分计划。设计阶段只确定方案，不创建成员。

任务总览至少包含：

```text
目标 / 预期结果 / 验收标准 / must-have 与 add-later / 执行方式 / 预计成员数
```

团队蓝图至少包含：角色、职责、能力配置、协作可见性、验证方式。按以下规则选择可见性（分阶段编排默认按专业流水线可见性）：立场需要相互独立的批判（评审、红蓝对抗）选对抗/交叉审查；立场中性、仅任务分区时选静态并行分解；兼具分区与批判时按对抗处理——隔离是更严格的可见性。

| 模式 | 可见性 |
|---|---|
| 对抗/交叉审查 | 成员互不可见，协调器不透传产出或摘要 |
| 静态并行分解 | 集成前互不可见，分别返回协调器 |
| 专业流水线 | 只读取已声明的前序产出 |
| 辩论 | 先隔离作答，互见阶段再转交原始观点 |

执行中需要改变可见性时，走“重新设计”，更新任务总览和后续派发规则；范式内执行方式或协作方式变化同样走“重新设计”；跨范式变化回到“触发与路由”，记录原分支是否仍可用。已完成成员按原模式收尾，未派发成员按新计划执行，在途成员按现状收尾（无法安全停止的判定与选项见“执行与变更”）。

写入隔离按三级选择：

| 层级 | 机制 | 适用 |
|---|---|---|
| L0 | 互斥文件/模块 | 默认方案（含无写入的只读任务）；同一文件的不同区间不算互斥 |
| L1 | 按依赖顺序或串行化时序启动 | 后序依赖前序产出，或用户接受串行消除同文件并发 |
| L2 | 每成员独立 worktree 与分支 | 同文件必改、强耦合并行或低级隔离反复失败 |

层级按表序自上而下优先，能被低层级满足时不升级。

蓝图定稿前执行反重叠测试：非同质角色的产出若可互相替代，重新划分职责；重划 2 轮仍不清晰则合并角色并更新计划。同质批量任务不因角色可互替而无限合并：职责由文件集划分，反重叠测试豁免同质 fan-out。当前运行时并发上限为 `P`、每代理工作量上限为 15 个文件时，按下式分批：

```text
每批容量 = P × 15
批次数 = ceil(文件数 / 每批容量)
本批代理数 = min(P, ceil(剩余文件数 / 15))
批间串行，每代理不超过 15 个文件；复杂文件按工作量折算并减少数量。
```

数量优先级为：运行时硬上限 > 用户明确数量 > 拆分自然数 > 经验默认值。每代理 ≤15 文件属于拆分自然数的工作量折算而非硬上限；用户数量使单代理负载超过该折算时，在计划说明负载并随确认门确认。实际数量与用户要求不同或反重叠测试合并角色时，说明原因并把有效数量写入计划。

拆分计划必须写明：

```text
子任务 / 负责人 / 读取范围 / 写入范围 / 可见性 / 隔离层级
验证方式 / 预算与降级路径 / 成员收尾方式
状态持久化：启用/跳过 / .team/ 文件与用途 / 保留、提交或清理范围
```

L2 时还要写入基线、worktree 路径、分支名、合并顺序和清理范围；先读取 `references/worktree-isolation.md`。只读任务不创建 `.team/`；允许写入且需要跨会话恢复、多阶段交接或长期跟踪时，才读取 `references/team-state.md`，并按拆分计划（经唯一启动确认）创建 `.team/`。

**唯一启动确认门**：把任务总览、团队蓝图与拆分计划一并交用户确认，确认后才创建成员或提交流水线。设计阶段不另设确认门。用户拒绝时终止当前方案；如果仍要完成任务并改选执行方式，回到“触发与路由”，流水线启动拒绝按 `references/workflow-orchestration.md` 处理。启动后的范围、成本、写入或可见性重大变化使用针对该变化的确认，不把它伪装成新的常规阶段。

### 3. 执行与变更

创建成员前读取 `references/platform-runtime.md` 和 `references/subagent-prompt.md`；每个 prompt 遵循 `references/subagent-prompt.md` 的必填项（重建类 prompt 按该文件的模板外规则）。辩论模式第一轮成员完成即自动结束时，在互见阶段重建成员，并在 prompt 中注入第一轮原始观点，不注入协调器判断（属确认门内计划动作，不另确认）。注入角色文件前过滤自动触发、平台专属工具、危险命令、自动安装和越权写入指令。默认不提交；L2 仅允许成员在自己确认的分支按增量提交。

按计划派发并维护成员 ID、任务、写入范围、状态和收尾结果；状态由协调器唯一维护，避免并发更新冲突。阶段转换以及成员完成、失败、阻塞或被接手时，逐个向用户播报状态：`✅ [角色] 完成: [结果]`、`❌ [角色] 失败: [原因/选项]`、`⚠️ [角色] 部分完成: [缺口]`、`⛔ [角色] 阻塞: [原因/下一步]`、`↪️ [角色] 已接手: [原因]`、`⏭️ [角色] 跳过: [影响]`、`🛑 [角色/批次] 熔断: [原因]`。执行中变更、取消和阶段转换用一句话文字播报，不限符号。成员保持空闲或需显式关闭而无工具时，如实记录“会话内仍可用”（完成即自动结束的成员除外）。

执行中的处理规则：

- **正常完成**：验证返回值和实际文件，继续当前阶段。
- **失败**：对话式团队立即报告并提供重试、跳过、接手或终止；流水线按错误策略收集逐项状态。配置类错误和普通运行错误按 `references/platform-runtime.md` 的不同重试上限处理，熔断立即停止继续派发，不等最终汇总。
- **阻塞**：补充上下文；平台没有可用通信/唤醒能力时先重建成员，仍无响应则由协调器接手。重建 prompt 携带原任务范围、已完成产出路径、阻塞原因、上一成员返回内容和剩余验收标准，并记录原因和收尾状态。
- **跳过**：标记为部分完成（有可用产出）或阻塞（无可用产出），重新计算依赖；依赖它的下游任务标记阻塞、随缺口交付处理，只继续不依赖该成员的任务，最终交付按带缺口规则处理。
- **部分完成**：先核对缺口，不能直接标记完成。原范围内缺口：关键路径上的由协调器直接补齐，其余由原成员补做（原成员已自动结束时按阻塞重建规则重建、携带剩余范围）；范围外缺口不交给原成员越权修改，派发新范围必须更新计划并经用户确认，或由协调器补齐（写入范围临时扩展统一记录于最终报告；补齐限已确认交付物的缺失部分，超出原目标的新工作走重新设计）；缺口可接受时，取得用户确认后带缺口交付并列明文件、影响和未完成原因。
- **执行中变更**：范围、成本、写入集、可见性或协作模式改变时进入“重新设计”；已完成成员不回溯，未派发成员采用新计划，在途成员按现状收尾（无法安全停止=中断会丢失不可恢复的中间状态，按任务原子性判定；此时交用户选择：等待当前回合完成、立即中断或放弃该成员产出）。
- **用户取消**：进入“终止并收尾”，对在途成员按平台停止能力处理（无任何停止能力时等待其完成当前回合后收尾并如实记录），不自动回滚业务路径产出，逐文件列出已写入清单和成员状态。

成员间交接遵循“产物走声明路径，协调走当前可用通信能力”；消息只发送路径和一句摘要。对抗/并行模式不得通过消息旁路可见性限制。辩论模式按 `references/subagent-prompt.md` 和 `references/team-state.md` 的隔离与互见规则执行。

### 4. 验证、交付与清理

1. 主协调器按任务总览验收标准检查实际文件、返回结果、范围和冲突；只读任务核对返回结果，不创建落盘产物。验收同时检查交付打磨：边界情况覆盖、命名与错误提示专业度、文档与示例完整性，影响验收标准的问题计入打回项，其余计入最终报告风险。
2. 质量不通过时打回修改并重新验收（打回对象：空闲成员唤醒，已结束成员重建并附打回历史，或协调器接手；分阶段编排的阶段验收同用本规则）；同一问题连续 3 轮仍未通过，停止自动修复并向用户提供：修改验收标准（走重新设计）、缩小范围（走重新设计）、重新派发（按打回对象规则重建或另派，附 3 轮历史）、协调器接手、经确认带缺口交付或终止并收尾。
3. 最终报告包含任务概述、执行方式、成员结果、实际修改、验证结果、风险、部分完成缺口、未完成原因和成员收尾状态（含未被显式释放的说明）。只有产出确实可运行或可部署时才附移交信息。
4. 按当前平台生命周期收尾成员：区分完成、保持空闲、中断当前回合、显式关闭和团队级释放；interrupt 不等于 close。
5. worktree、分支和 `.team/` 只清理计划中登记且获授权的精确目标。合并、废弃、保留和清理分别报告；取消时保留业务路径产出并交用户决定去留。

## 最终质量闸门

最终回复前逐项检查（无成员的任务跳过成员相关项）：

- 所有子任务均已完成，或明确标记失败、部分完成、阻塞、接手、跳过、未开始及原因。
- 实际修改没有超出确认的写入范围；范围变化有记录（确认要求见对应决策点：新范围派发、重新设计、重大变化针对性确认）。
- 运行了与任务匹配的验证，结果与最终报告一致。
- 没有把成员产出未经验收直接拼接进结论。
- 所有已创建成员都有最终状态和真实收尾结果。
- 没有把 interrupt、回合结束或停止派发表述成成员已关闭或资源已释放。
