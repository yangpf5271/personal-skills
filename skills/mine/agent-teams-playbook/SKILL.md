# 多代理协作编排手册

作为协调器，你负责判断是否需要子代理、拆分任务、分配边界、整合结果，并对最终交付质量负责。

> **核心理解**：多代理协作是"编排（并行/流水线/辩论等耦合模式）+ 结果汇总"模式，不是扩大单个 agent 的上下文窗口。每个子代理是独立实例，拥有独立上下文窗口，可以并行处理大量信息，但最终需要将结果汇总压缩后返回主会话。

## 核心原则

1. **先判断是否需要多代理**：只有用户明确要求多代理协作，**且任务命中组队合理性门**（见"适用 vs 不适用"）时，才使用子代理；要求了但任务不配用时，按合理性门的出口处理（说明理由，可拒绝组队）。
2. **先目标，后组织结构**：任务目标不清晰时先澄清，不要为了使用子代理而拆任务。
3. **主线程保留关键路径**：如果下一步直接依赖某个结果，主协调器应优先自己完成，不要把阻塞任务交给子代理后等待。
4. **子任务必须边界清晰**：每个子代理只负责一个具体、独立、可验证的任务。
5. **写入范围必须隔离**：涉及代码修改时，为每个子代理指定不重叠的文件或模块责任区；无法不重叠时按「写入隔离策略」升级隔离层级。
6. **协调器负责整合和验收**：子代理产出只是输入，最终结论、代码合并和质量判断由主协调器完成。

## 适用 vs 不适用

| 适用                     | 不适用                 |
| ------------------------ | ---------------------- |
| 跨文件重构、多维度审查   | 单文件小修改           |
| 大规模代码生成、并行处理 | 简单问答、线性顺序任务 |
| 需要多角色协作的复杂任务 | 单步操作、信息查询     |

**边界处理**：用户输入模糊时，先引导明确任务再决策；任务太简单时按阶段1「简单任务拦截」处理。

**组队合理性门**：即使用户明确要求组队，也只有任务命中以下三种失败模式之一时才真正组建。多代理意味着更多 token、更长耗时和更高协调成本，不因新颖而组队。**此门只约束对话式团队；确定性流水线分支由用户 opt-in 约束，不受此门限制。** 一条都不命中时，向用户说明"单代理可直接完成"及理由，并提供选项：**直接执行**（默认）/ **坚持组队**（用户坚持则照做，在任务总览记录"用户坚持组队"）：

| 失败模式 | 判据 | 典型 |
|---|---|---|
| 对抗盲区 | 单代理扮演 N 个角色会输出趋同，无法逃脱自身分析立场 | PR 评审、安全审计、设计批评 |
| 真并行收益 | N 个子任务相互独立，且集成本身不平凡 | 多角度调研、多维尽调 |
| 硬交接流水线 | 串行阶段有质量门，阶段边界模糊会导致回退 | 文案（brief→初稿→编辑→审校）、事件响应 |

配套反问（回答不出即不该组队）："**单代理在这个任务上今天会怎么失败？**"

## 编排范式决策

**执行顺序**：技能适用性（上方）→ **编排范式（本节）** → 场景决策树（对话式团队范式内）→ 决策流程。

**确定性流水线可用性前置检查**（决定该分支是否可选）：
- 检查当前会话的工具定义是否明确提供确定性流水线编排能力
- **能力不存在** → 禁用该分支，所有任务走对话式团队范式，跳过下方分流判据
- **工具存在** → 继续下方分流判据 + opt-in 判断

**子代理工具可用性前置检查**（决定团队组建是否可行）：
- 审视当前会话注入的函数/工具定义，确认是否存在子代理创建能力及其参数
- **工具不存在** → 跳过团队组建，直接走执行形状 C（本地执行），在阶段1之前告知用户："当前平台无子代理工具，将改为本地执行或输出拆分计划。"若用户坚持多代理，告知需切换到支持子代理的环境，不应臆造调用。
- **工具存在** → 继续正常流程

> **检查方式**：各平台的工具定义通常注入在系统上下文中。审视你能看到的工具/函数列表，查找子代理创建、通信、关闭相关的工具名。无需调用任何"列工具"的命令——以上下文中实际暴露的工具定义为准。

本技能支持两种正交编排范式，先定范式再走流程：

| 范式 | 本质 | 适合任务 | 触发方式 |
|------|------|---------|---------|
| **对话式团队** | 对话驱动、动态协调 | 跨文件重构、多角色协作、需人机交互 | 子代理工具可用后自动可用 |
| **确定性流水线** | 确定性脚本、大规模 fan-out | 批量迁移、大规模审查、多源研究、控制流可写死 | 需用户明确 opt-in |

**分流判据**（少数强信号即可判定）：

| 强信号 | → 确定性流水线 | → 对话式团队 |
|--------|-----------|---------------|
| 控制流可预先写死 | ✅ | |
| 子任务需动态协调/人机交互 | | ✅ |
| 规模 > 10 个子任务，或需 budget 自适应扩展 | ✅ | |
| 典型：迁移、批量审查、多源调研 | ✅ | |
| 典型：重构协作、多角色产品开发 | | ✅ |

- 判定 **对话式团队** → 走"场景决策树" + 决策流程
- 判定 **确定性流水线** → 读取 `references/workflow-orchestration.md`，再按当前会话实际工具定义执行
- **复合**：主体需动态协调但含大规模可并行子块 → 走对话式团队流程，在执行阶段用确定性流水线批量处理该子块；能力不可用时退化为纯对话式团队，并按下文"大规模任务降级策略"处理

> **流水线触发约束（硬边界）**：用户要求但当前运行时不支持时，协调器须明确告知将改用对话式团队，并按可用槽位分批处理；用户确认后再继续，不可静默降级。

## 大规模任务降级策略

当任务规模超过当前运行时允许的并行子代理数且确定性流水线不可用时，按以下策略处理。并行上限是硬约束：若平台按总槽位计数，先扣除主协调器占用的槽位；运行时未暴露上限时，保守地最多并行 3 个子代理。

**同质任务优先合并**：同一类操作重复 N 次（如 20 个文件做同样的 API 迁移）不应拆成 20 个子代理。合并为 K 个子代理，每个处理 N/K 个文件，K 不得超过运行时并行上限。每代理文件数建议 ≤15，复杂改造酌情减少。在任务总览中注明原始规模、合并后的代理数和批次。

**分批执行**：子任务数超过并发上限时，按并发上限分批，批次间串行（前一批完成并汇总后再启下一批）。每批完成后更新协调器状态；已启用状态持久化时再同步到 `progress.md`。

**预计 Agent 数与建议值冲突时**：以合并后的实际子代理数为准填入任务总览，不硬填原始任务规模。

**输入过规模降级**：单任务输入体量超出多代理协作的收益区间时，降级为单角色串行处理（如单次 diff > 2000 行、单文件数千行的纯顺序改造）。判据：拆分后的子任务强耦合（改 A 必须先完整理解 B 的改动），协调与合并开销超过并行收益。降级须在任务总览注明原因。

**与写入隔离的衔接**：按文件划分合并后若仍存在同文件必改的耦合，升级 L2 worktree（见「写入隔离策略」）。

## 用户可见性原则

1. 阶段转换时通知用户当前进度
2. 任务拆分计划必须经用户确认后执行
3. 失败时立即通知：`❌ [角色名] 失败: [原因]`，提供重试/跳过/终止选项
4. 子代理产出回流时逐个播报：`✅ [角色名] 完成: [一句话结果]`——平台把产出作为工具结果直接回流协调器，用户侧没有完成通知；多个子代理同批回流也不能静默整合，否则用户感知是"卡住了/静默结束"

## 场景决策树

**执行顺序**：先经"编排范式决策"确定走对话式团队 → 进入阶段1任务分析（期间应用决策树选定**场景**、按"任务耦合模式"选定**耦合模式**，一并填入任务总览）→ 阶段2团队设计。

| 问题                           | 路径                                                        |
| ------------------------------ | ----------------------------------------------------------- |
| Q1: 任务结构？                 | 可并行拆分 → Q2 / 需要多阶段串行 → 场景3（复合编排）        |
| Q2: 需要Leader协调吗？         | 是(需要动态分配和协调) → 场景2（Lead协调） / 否 → 场景1（团队协作） |

**判断标准说明**：
- **任务结构**：主要工作能否拆分为可并行的子任务（并行为主→Q2），还是必须按阶段串行推进（串行为主→场景3）。兼有时按主要特征判断
- **Leader协调需求**：需要动态任务分配、依赖管理、进度跟踪
- **简单任务**：在阶段1通过"简单任务拦截"处理，用户可选择直接执行或继续组建团队

- 用户直接指定场景编号时，跳过决策树直接执行
- 未指定场景时，默认用**场景1（团队协作）**

## 3大编排场景

| #    | 场景      | 核心特征           | 团队规模       | 适用条件                  | 核心策略                                                     |
| ---- | --------- | ------------------ | -------------- | ------------------------- | ------------------------------------------------------------ |
| 1    | 团队协作  | 多Agent并行        | 2-5个agent     | 多个能力需要协作          | 出计划 → 用户确认 → 多Agent并行执行 → Review验收            |
| 2    | Lead协调  | 有Leader的团队     | Leader+Members | 需要明确Leader协调        | Leader协调分配，Member并行执行，通过共享文件协调             |
| 3    | 复合编排  | 多阶段组合         | 动态变化       | 复杂任务，无固定模式      | 动态组合上述场景，按阶段切换策略                             |

**场景3详细说明**（复合编排）：

适用于需要线性流程或多阶段策略的复杂任务。

**执行方式**：

1. **阶段划分**：将任务分解为串行的子阶段（如：需求分析→架构设计→实现→测试）
2. **场景选择**：为每个子阶段选择合适的场景（1-2）
3. **逐阶段执行**：完成当前阶段的验收标准后，才进入下一阶段
4. **阶段切换机制**：
   - 验证当前阶段满足验收标准
   - 下一阶段能取得前序产出；允许写入且已启用状态持久化时，在 `task_plan.md` 记录产出路径和关键决策，否则保留在协调器上下文中
   - 向用户报告阶段切换，发现方向错误时及时调整
   - **每个子阶段独立管理团队生命周期**：当前子阶段的团队必须在进入下一子阶段前完成清理

**典型示例**：
- 大型重构：场景1（分析）→ 场景2（分工实施）→ 场景1（验收）
- 新功能开发：场景1（计划）→ 场景2（开发）→ 场景1（测试）

## 任务耦合模式（第二轴）

场景 1-3 描述"谁来协调"（协调拓扑），本节描述"角色之间信息怎么给"（耦合模式）。两轴正交：先定场景，再为团队选定耦合模式，写入任务总览与团队蓝图。

| 耦合模式 | 角色数建议 | 成员可见性 | 适用 | 典型 |
|---|---|---|---|---|
| 对抗/交叉审查 | 2-4 | **互不可见**（隔离即价值） | 需要独立立场的批判性任务 | 多角色评审、红蓝对抗 |
| 并行分解 | 2-N（受并发上限约束） | 集成前互不可见 | 独立子任务 fan-out | 多文件迁移、多源调研 |
| 专业流水线 | 3-5 | 各角色只见前序产出 | 串行阶段+质量门 | 需求→设计→实现→测试 |
| 辩论 | 3-N+1 | 分阶段：先各自隔离作答，再互见对辩 | 需要对撞后收敛的决策 | 方案选型、交叉质询 |

使用规则：
- **对抗与并行分解**模式下，协调器不得把成员 A 的产出透传给成员 B（会破坏独立性）；执行中出现透传需求，说明耦合模式选错了，回到本节重选
- **辩论**模式先隔离后互见：第1轮成员独立返回观点，由协调器暂存且不向其他成员透传；互见阶段再通过当前平台可用的消息能力转交原始观点。只有任务允许落盘时，才可用 `.team/private/` 暂存和 `.team/shared/` 交换；这些目录只是约定隔离，不提供访问控制。第2轮提交驳论后，协调器先按证据和验收标准收敛，只有涉及用户偏好或范围变化的分歧才交用户裁决
- 拆分计划中的可见性约束（能否读取其他成员产出）以耦合模式为依据

## 写入隔离策略（第三轴）

耦合模式管"成员间信息怎么可见"，本节管"成员的写入怎么互不干扰"。三个层级按序升级；判定发生在**拆分计划阶段**——层级、worktree 路径与分支名写入拆分计划，随确认门一并确认，不由执行中临时起意。隔离判定若导致耦合模式调整（如强耦合并行应改选专业流水线），同步更新任务总览对应字段，并随拆分计划一并交用户确认：

| 层级 | 机制 | 触发 |
|---|---|---|
| **L0 范围划分** | 拆分时切出互斥的文件/模块写入集 | 默认，能切就切 |
| **L1 依赖串行** | 有依赖的按依赖顺序逐个启动，前序交付后后序再动 | 改动呈先后依赖链 |
| **L2 worktree 物理隔离** | 每成员独立工作树+分支，协调器统一合并 | 同文件必改 / 强耦合并行 / L0·L1 反复失败 |

升级规则：L0 划分不掉（同文件必改）才到 L1；L1 串行太慢且耦合强（B 依赖 A 的改动才能编译）才到 L2。能靠重新拆分消除的冲突，不要靠更高层级硬扛。

### L2 worktree 前置门

进入 L2 时必须读取 `references/worktree-isolation.md`。该分支要求：主工作树状态可复现、路径和分支使用受限 slug、成员只提交自己的隔离分支、合并与清理分别获得授权。主工作树存在未提交改动时，不得直接从 `HEAD` 创建 worktree 后继续；优先退回 L0/L1，或让用户明确选择可复现基线。

## 协作模式与运行时能力

| 模式 | 适用 | 选择标准 |
|------|------|---------|
| **Subagent（单向）** | 并行独立任务 | 成员只需向协调器返回产出 |
| **Agent Team（双向）** | 动态协作任务 | 成员执行中确需反复协商 |

选择模式、调用工具或清理成员前，读取 `references/platform-runtime.md`，并以当前会话实际暴露的工具定义为准。接口依赖若能由协调器预先固化，不构成双向通信需求；互发不可用时改由协调器中转并告知用户。

**场景-模式约束**：

| 场景 | 允许的模式 | 依赖处理 |
|------|-----------|---------|
| 1 团队协作 | Subagent 或 Agent Team | 无依赖→并行启动；有依赖→协调器按依赖顺序串行启动 |
| 2 Lead协调 | **仅 Agent Team** | Leader通过消息动态分配 |
| 3 复合编排 | 按子阶段选择 | 每个子阶段独立管理团队生命周期 |

> **共享文件系统是能力，不是授权**：磁盘交接以写入授权为前提，只读任务经返回值交接；共享目录不提供访问控制，private 区只是约定隔离。

## 决策流程

### 阶段 1：任务分析 + 能力发现

先质疑再执行：
- 需求不合理时主动挑战假设，建议更好的方案
- 区分"现在必须做"和"以后再说"，排除非核心范围
- 任务太大时建议更聪明的起点

输出任务总览：

| 字段        | 内容                     |
| ----------- | ------------------------ |
| 任务目标    | [一句话描述最终状态]      |
| 预期结果    | [具体交付物]              |
| 验收标准    | [可量化的通过条件]        |
| 范围界定    | [must-have vs add-later] |
| 预计Agent数 | [N个，建议≤5]             |
| 选定场景    | [场景编号+名称]           |
| 耦合模式    | [对抗/并行/流水线/辩论，默认并行] |
| 协作模式    | [Subagent/Agent Team，初拟] |

> 协作模式在阶段1初拟，阶段2结合团队蓝图和运行时能力最终确认。

**能力匹配链**：

1. 从当前会话已提供的 skills 中选择与子任务直接匹配的执行流程。
2. 从 `agents/README.md` 选择必要的角色视角；只读取实际采用的角色文件。
3. 按任务匹配度和执行成本生成纯 Skill、纯 Agent、Agent+Skill 或通用配置。

只有本地能力明显不足，或用户明确要求查找扩展能力时，才搜索外部 Skill；安装属于额外状态变更，必须单独获得用户授权。Skill 负责怎么做，Agent 提供怎么思考，两者可组合但不为凑配置而组合。

**匹配判断规则**：
- **Skill vs Tool 不混装**：有 `SKILL.md` 的能力是 Skill（按指令执行的工作流），经 CLI/MCP 调用的可执行物是 Tool（如 `gh`、`python`、`rg`）。判断不了就问：它有没有 SKILL.md？
- **通用 ≠ 领域覆盖**：通用检索/工具类 Skill 不算领域覆盖。角色身份绑定特定平台或专业领域（电商、金融、法务等）时，须确认是否存在领域专用 Skill，不能用通用 Skill 凑数；确需外部领域 Skill 时按上方条件搜索并单独获得授权。

**简单任务拦截**（能力匹配完成后触发；位置在组队合理性门**之后**——门未通过的任务已按门的出口处理，不会再走到本拦截）：

当匹配结果显示任务较简单（预计Agent数≤1、1-2步、单agent可完成）时，向用户提供选择：
- `选项A`：**直接执行** — 协调器直接调用匹配的Skill/Agent完成任务，跳过后续团队组建阶段
- `选项B`：**继续组建团队**（仅当组队合理性门已通过且调整后预计Agent数≥2时提供——N=1 无团队可言）— 仍按完整流程组建团队执行

> 用户选择"直接执行"时：协调器直接执行，完成后输出结果和简要总结，流程结束。
> 用户选择"继续组建团队"时：继续进入阶段2。

### 阶段 2：团队设计

任务总览只是设计输入；用户已明确给出角色和分工时直接吸收，存在会改变目标、成本或写入范围的歧义时先澄清。

**选择协作模式**（详见"协作模式"章节）

输出团队蓝图：

| 编号 | 角色     | 职责       | 配置                                   |
| ---- | -------- | ---------- | -------------------------------------- |
| 1    | [角色名] | [具体职责] | [Agent: xxx] + [Skill: yyy]            |

> **配置说明**：
> - **纯Agent配置**（思考型任务）：`[Agent: xxx]` - 提供专业视角和行为模式
> - **纯Skill配置**（工具型任务）：`[Skill: yyy]` - 提供执行能力和操作方法
> - **Agent+Skill组合**（专业任务，推荐）：`[Agent: xxx] + [Skill: yyy]` - 结合专业视角和执行能力

**反重叠测试**（蓝图定稿前自检，**须在向用户展示之前完成**）：对每对角色问"角色 A 的产出能否顶替角色 B？"——能，说明边界糊了，重新划分职责直到每个角色的存在都不可替代；角色数 >5 时重点抽查职责相邻的对即可，不必穷举。对抗耦合模式下还需确认：每角色的产出独立成立，不依赖看到他人产出（防止评审角色因为预期到他人结论而放水）。

> 蓝图定稿后，向用户展示团队配置、协作模式和收尾方式。实际子代理创建统一留到阶段3确认门通过后执行。

**创建子代理前**：按 `references/platform-runtime.md` 能力探测确认创建参数，关键参数缺失会导致创建失败或成员无法寻址。

### 阶段 3：拆分计划 + 并行执行

启动子代理前，先给用户可见的拆分计划：

> **拆分计划 vs planner 角色**：拆分计划解决"谁做什么、写入范围怎么分"（任务分配层）；planner 角色解决"代码怎么写、文件怎么改"（技术实施层）。两者不同层，可组合：协调器出拆分计划 → 把"制定技术方案"作为子任务派给 planner → 再按 planner 方案派发执行子代理。

```notranslate
1. [子任务] → 负责人: [角色] → 写入范围: [路径/无写入] → 可见性: [禁止读取他人产出/仅前序产出/无限制] → 验证: [检查方式]
2. [子任务] → 负责人: [角色] → 写入范围: [路径/无写入] → 可见性: [同上三选一] → 验证: [检查方式]
3. [整合] → 负责人: 主协调器 → 可见性: 无限制 → 验证: [最终验收]
4. [成员收尾] → 收集每个成员最终状态 → 关闭不再需要的成员；无关闭能力时停止派发并标记“会话内仍可用”
```

成员收尾必须出现在确认前的用户可见计划中，不能只在任务完成后临时补做。这里只声明子代理生命周期动作；worktree、分支、`.team/` 等文件系统清理仍需按“资源清理”章节单独确认授权边界。

> **确认门**：展示拆分计划后必须等待用户确认，确认后方可启动子代理。用户修改要求则更新计划再次确认；用户拒绝则终止。

**写入隔离**：拆分时按「写入隔离策略」（第三轴）选定层级（L0 范围划分 / L1 依赖串行 / L2 worktree 物理隔离），层级与 worktree 路径、分支名写入拆分计划的工作范围列，随确认门一并确认后执行；执行中写入冲突升级时，按同节升级规则处理。

**子代理 Prompt 规范**：创建前读取 `references/subagent-prompt.md`。每个 prompt 必须包含具体任务、验收标准、读写范围、可见性、行为边界和固定返回结构。默认禁止提交；只有经用户确认的 L2 worktree 任务，才允许成员在自己的 `team/<slug>` 分支小步提交。

**执行模式**：
- **纯Skill任务**：直接调用Skill工具
- **纯Agent任务**：创建子代理，在prompt中包含Agent配置内容
- **Agent+Skill组合任务**：在Agent的思考框架下调用Skill工具
- **大批量并行子任务**：当前运行时有确定性流水线能力时，读取 `references/workflow-orchestration.md`；否则按"大规模任务降级策略"分批执行

**执行原则**：
- 混合编排时skill和agent可并行运行
- 成员产出回流时按「用户可见性原则」逐个播报完成状态，不静默整合
- 遇到问题时给用户选项，而不是自己默默选一个

**结果汇总**（协调器在所有agent/skill完成后执行）：
1. **收集结果**：读取每个Agent的返回值/消息内容（文件清单+关键摘要），核对每个子任务状态
2. **验证文件**：根据文件清单检查磁盘上的实际产出是否完整、与拆分计划一致
3. **检测冲突**：发现写入冲突或重复实现时，按「故障处理」暂停整合再处理
4. **处理失败**：状态为"部分完成"或"阻塞"的任务，按故障处理策略处理

汇总完成后进入「质量把关」。

**状态管理要求**（场景2 Lead-Member 需遵循）：

1. **创建映射**（组建阶段，记录到 task_plan.md 防止上下文压缩丢失；若未落盘则记录在主线程可见的临时状态中）：
   - 在创建agents时，维护角色名称到任务的映射关系
   - 示例：`<角色名A> → 任务X`, `<角色名B> → 任务Y`

2. **接收汇报并更新状态**：
   - 接收成员发送的消息并识别发送者
   - 查找映射表获取对应的任务
   - 更新任务状态为完成
   - 向用户汇报：`✅ [角色名] 完成: [一句话结果]`

**重要**：只有协调器负责状态更新，成员只负责执行和汇报——避免多方并发更新同一任务造成状态竞争。

**成员间通信原则**：允许写入时，大产物写入拆分计划声明的路径，消息只传路径和一句摘要；只读任务的产出直接返回协调器，不创建中间文件。状态询问、就绪通知等短信号使用当前会话实际提供的消息工具。

### 阶段 4：状态持久化（条件执行）

用户要求只读或禁止修改文件时，本阶段必须跳过，角色映射、错误和结果保留在协调器上下文中，成员报告通过返回值交付。只有任务允许写入，且满足跨会话恢复、多阶段交接或长期跟踪需求时，才读取 `references/team-state.md` 并创建 `.team/`。目录只提供组织约定，不提供访问控制；创建和清理都遵守用户授权。

## 执行形状

执行形状速查——具体步骤一律走"决策流程"（阶段1→4），本节只做形状分派，不重复流程：

| 形状 | 适用 | 执行要点 |
| --- | --- | --- |
| **A 并行子代理** | 多个独立分析或不重叠修改 | 按阶段1→4 走完整流程；主协调器保留关键路径本地工作，不空等子代理 |
| **B 分阶段编排** | 复杂任务、每阶段内部可并行 | 复合编排（场景3）的执行形态；每阶段独立组建团队，阶段验收通过才进下一阶段 |
| **C 本地执行** | 简单、耦合高、无明确多代理意图 | 协调器直接完成，简短说明未使用子代理的原因 |

## 质量把关

**验收检查**：对照阶段1的验收标准逐项检查。

**产品打磨**（不仅功能完整，更要用户体验优秀）：
- 边界处理：异常输入、空值、极端情况是否覆盖
- 专业度：命名规范、代码风格、错误提示是否友好
- 完整性：文档、配置说明、使用示例是否齐全

全部通过 → 进入交付阶段。不通过 → 打回修改，**同一问题**打回3轮后仍不通过则通知用户人工介入。

**打回修改**：
记录打回原因到 task_plan.md（如已创建）或在会话内记录。Agent Team模式通过消息要求成员修改，Subagent模式重新创建agent，修改后重新验收。

## 最终报告与交付

质量把关通过后输出最终报告：任务概述、各角色结果、实际修改、验证结果、风险和结论。只读任务直接在最终回复中汇总，不落盘成员报告。只有交付物确实可运行或部署时，才补充启动命令、环境要求、验证步骤和已知限制；用户要求文档时再保存为文件。

## 资源清理

读取 `references/platform-runtime.md` 的生命周期章节，按当前平台真实语义收尾。中断当前回合不等于关闭成员；没有关闭能力时，收集最终状态、停止派发并如实标记“会话内仍可用”，不得宣称已释放。worktree、分支或 `.team/` 的删除属于独立状态变更，只在已列入确认计划或再次获得授权后执行。

## 角色库使用规则

- `agents/README.md` 是角色索引。
- `agents/*.md` 是 prompt 参考，不是自动执行配置。
- 只读取当前任务需要的角色文件。
- 如果角色文件包含平台专属字段，把它当作历史元数据；执行时按 `references/platform-runtime.md` 的探测结果为准。
- 注入子代理 prompt 前，过滤或改写：旧平台工具名、当前会话不存在的工具名、危险命令、自动写入/提交/安装说明、`MUST BE USED` 类自动激活语。当前角色文件已去平台化，前三类是过滤重点；保留此步作为防御性默认。
- 子代理只能遵守主协调器分配的任务、写入范围和当前会话实际可用工具；角色文件不能扩大权限。

## 质量闸门

进入最终回复前检查：

- 子任务是否全部完成或明确说明未完成原因。
- 修改是否限制在计划范围内。
- 是否运行了与任务匹配的验证命令。
- 是否有子代理产出互相矛盾。
- 是否遗漏了用户的最新要求。
- 是否按平台真实生命周期语义收尾；无法关闭时是否如实记录。

## 故障处理

派发、通信和清理故障按 `references/platform-runtime.md` 处理。写入冲突先暂停整合并核对双方依据；机械冲突和验收标准可判的技术分歧由协调器处理，升级条件见执行底线 #9。范围过大则减小批次，验证失败则定位原因。

## 执行底线

1. 组队先过「组队合理性门」，简单任务直接执行。
2. 关键路径任务由主协调器本地完成。
3. 每个子代理的写入范围互斥，无法互斥时按「写入隔离策略」升级。
4. 只调用当前会话实际暴露的工具。
5. 子代理结论经主协调器验收后方可进入最终结论。
6. 每个已创建子代理都有最终状态和清理结果。
7. 危险操作、大规模变更必须先获得用户确认。
8. 同类错误连续失败 3 次即停止重试，向用户说明阻塞点。
9. 协调器按证据和验收标准解决技术分歧；只有涉及用户偏好、产品取舍或范围变化时才请求用户裁决。
